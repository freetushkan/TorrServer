# Форк freetushkan/TorrServer

Форк = **релизный тег апстрима + несколько линейных коммитов** поверх него.
Никаких merge-коммитов с апстримом: при выходе нового тега коммиты форка
переносятся (rebase) на него, `master` перезаписывается, релиз помечается
тегом `<тег апстрима>.MU.rN` (например `MatriX.147.1.MU.r1`).

Коммиты форка:

1. `feat(peruser): per-user torrents and viewed marks` — разделение данных по пользователям;
2. `chore(fork): tooling…` — эта папка и `.github/workflows/fork-upstream-sync.yml`.

## Перенос на новый тег апстрима

Автоматически: workflow **Fork upstream sync** раз в сутки смотрит теги
YouROK/TorrServer. Если вышел новый — пробует перенос и открывает issue:

- `Upstream <тег>: ready` — всё собралось, тесты и проверки прошли, ветка
  `sync/<тег>` запушена; в issue три команды, чтобы опубликовать;
- `Upstream <тег>: needs attention` — конфликт или что-то не собралось; в issue лог.

Вручную (то же самое, локально):

```sh
fork/rebase-onto.sh              # на самый свежий тег MatriX.*
fork/rebase-onto.sh MatriX.148   # на конкретный
# при конфликте: поправить, git add …, git rebase --continue, затем
fork/rebase-onto.sh --verify     # сборка + тесты форка + check-peruser.sh
git push --force-with-lease origin sync/MatriX.148:master
git tag MatriX.148.MU.r1 && git push origin MatriX.148.MU.r1   # запустит ts_release
```

Скрипт включает `git rerere`: однажды разрешённый конфликт при повторном
переносе (abort → заново) применится сам.

**Не пушьте теги апстрима в форк** (`git push --tags`): `ts_release.yml`
собирает релиз на любой тег.

## Как разрешать конфликты

Вся логика — в новых файлах, они никогда не конфликтуют:

| файл | что внутри |
|---|---|
| `server/settings/peruser.go` | флаг/настройка, список аккаунтов, ключи «просмотрено», LastUser, хранилище владельцев, стартовая миграция |
| `server/torr/peruser.go` | `AddTorrentForUser`, `RemTorrentForUser`, `ListTorrentForUser` |
| `server/web/api/peruser.go` | `currentUser`, `requestUser`, `userParam`, `settingsForUser` |
| `web/src/components/Settings/PerUserSettings.jsx` | переключатель в настройках + его переводы |

В апстримных файлах только однострочные хуки, помеченные комментарием
`fork: per-user data`. При конфликте **берите сторону апстрима и заново
ставьте хук** — полный список хуков с точным текстом в начале
`fork/check-peruser.sh`. Если функцию в апстриме переписали — хук ставится
в аналогичное место новой версии.

`fork/check-peruser.sh` после переноса проверяет две вещи:

1. все хуки на месте (конфликт, решённый «в пользу апстрима», может молча
   выкинуть хук — а компилироваться всё будет);
2. в HTTP-обработчиках нет обращений к торрентам и отметкам «просмотрено» в
   обход обёрток — так обычно протекает изоляция, когда апстрим добавляет
   новый эндпоинт. Осознанные исключения — в `fork/peruser-allow.txt`
   (строка кода целиком: если апстрим её поменяет, скрипт спросит снова).

## Как устроено разделение по пользователям

Включается флагом `--peruserdata` (принудительно) или переключателем
«Разделение данных по пользователям» в настройках. Имеет смысл только с
`--httpauth`; аккаунты берутся из `accs.db`.

Хранение (bbolt/json через общий `tdb`):

| bucket | ключ | значение |
|---|---|---|
| `TorrentUsers` | hash | JSON-массив аккаунтов-владельцев |
| `Viewed` | `<user>:<hash>` | отметки пользователя (просто `<hash>` — общие) |
| `LastUser` | hash | кто последним смотрел список / делал preload |
| `PerUser` | `owners_migrated` | признак, что старое поле `TorrentDB.users` импортировано |

Правила:

- у торрента нет владельцев → он общий, его видят все;
- добавил новый торрент → владелец только ты; добавил чужой → ты добавляешься к владельцам;
- удалил → ты убираешься из владельцев; торрент удаляется, когда владельцев не осталось;
- чужой торрент удалить нельзя; аккаунты, удалённые из `accs.db`, игнорируются;
- отметки «просмотрено» у каждого свои; общие отметки, сделанные до включения
  режима, копируются пользователю при первом обращении;
- плейлисты получают `&user=<логин>`, чтобы неавторизованный плеер отмечал
  просмотр нужному пользователю; если параметра нет — берётся `LastUser`.
  `?user=` влияет **только** на отметки, владение меняют лишь авторизованные запросы.

Не изолированы (видят всех): DLNA, WebDAV/FUSE (`torrfs`), Telegram-бот, MCP,
а также `get`/`set` торрента по хэшу.

## Отличия от ветки на MatriX.141

Перенос был заодно перестроен под лёгкие обновления:

- владельцы хранятся в отдельном bucket вместо нового поля в
  `Torrent`/`TorrentDB`/`TorrentStatus` — апстримные структуры не тронуты;
  старое поле `users` импортируется один раз при старте;
- пользователь запроса передаётся через контекст запроса — сигнатура
  `torr.Stream` апстримная;
- переводы регистрируются из компонента — JSON-файлы локалей не тронуты;
- торренты без владельцев видны всем сразу, а не после рестарта;
- нельзя удалить торрент, владельцем которого является только другой пользователь;
- `?user=` экранируется и больше не даёт стать владельцем;
- убраны отладочные логи из `play()`; поле `users` больше не отдаётся в статусе торрента.
